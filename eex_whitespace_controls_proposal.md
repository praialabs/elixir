# Proposal: Explicit Whitespace Controls for EEx (`<%-` and `-%>`)

## Rationale & Problem Description

When generating code or text files using EEx templates (such as in `mix new`, Phoenix installer `phx.new` and related generators, or custom code generators), template authors frequently struggle with (or ignore) unintended whitespace accumulation around block control expressions (e.g., `<%= if condition do %>...<% end %>` or `<%= for item <- items do %>...<% end %>`).

To keep templates readable, control flow tags are naturally placed on dedicated lines. However, EEx treats surrounding newlines as literal text. As a result, rendered outputs often contain unwanted blank lines, leading indentation, or missing EOF newlines.

### Evidence from Core & Ecosystem

This issue is a recurring source of maintenance overhead across the Elixir ecosystem:

1. **Elixir Core (`mix new`)**:
  - PR [#15710](https://github.com/elixir-lang/elixir/pull/15710)
2. **Phoenix Framework Installer (`phx.new`)**:
  - PR [#6712](https://github.com/phoenixframework/phoenix/pull/6712)
  - PR [#5657](https://github.com/phoenixframework/phoenix/pull/5657)
  - PR [#2490](https://github.com/phoenixframework/phoenix/pull/2490)
  - PR [#1436](https://github.com/phoenixframework/phoenix/pull/1436)

Without tag-level whitespace controls, template maintainers must resort to awkward workarounds (such as squeezing tag delimiters onto adjacent lines), which compromises code legibility and is error-prone.

### Templating Whitespace-Sensitive Formats (YAML & JSON)

Beyond Elixir source generators, EEx is often used to generate configuration files and infrastructure manifests, such as YAML (Kubernetes/OpenShift) or JSON documents.

In indentation-sensitive formats like YAML, unexpected newlines or stray whitespace generated by block tags (`<%= if ... %>`, `<%= for ... %>`) can corrupt document structure, inject invalid syntax, or introduce unexpected empty list items. Global options like `trim: true` are unusable in YAML because document semantics strictly depend on preserved line breaks and indentation. Fine-grained tag-level controls (`<%-` and `-%>`) allow authors to format template logic cleanly without risking YAML or JSON parsing failures.

## Comparison with Existing Alternatives in Elixir

Template authors currently have three main workarounds, all of which present significant drawbacks:

1. **Global `trim: true` Option in EEx**:
   - *How it works*: Automatically removes empty lines around EEx tags template-wide.
   - *Drawback*: `trim: true` is an "all-or-nothing" setting. It strips empty lines indiscriminately across the entire file, which breaks intentional formatting (such as blank lines between function definitions, Markdown sections, struct fields, or configuration blocks) and corrupts indentation-sensitive files like YAML.

2. **Manual Inline Tag Formatting**:
   - *How it works*: Placing open/close tags directly adjacent to text content (e.g. `Text content<%- if @cond do %>More text<% end %>`).
   - *Drawback*: Severely degrades template readability and makes complex nested control flow difficult to audit or maintain. I believe this is the most common workaround in the Elixir ecosystem today.

3. **Post-Processing Output Strings**:
   - *How it works*: Passing the rendered template string through `Code.format_string!/1` or regex/string cleaning functions (`String.trim/1`).
   - *Drawback*: Code formatters only work for valid Elixir source code. They cannot be used for generating YAML, JSON, Markdown, HTML, Shell scripts, Dockerfiles, `.gitignore`, or arbitrary config files. In whitespace-sensitive formats, unexpected whitespace makes documents invalid before any post-processing can even run.

## Prior Art in Other Languages & Ecosystems

Fine-grained tag-level whitespace trimming is the standard solution across major programming language template engines:

- **Go (`text/template`, `html/template`)**: Added in [Go 1.6 (2016)](https://go.dev/doc/go1.6#template) via proposal [golang/go#9969](https://github.com/golang/go/issues/9969), supporting both `{{-` (left-trim) and `-}}` (right-trim) natively in template syntax. (Extensively used in Kubernetes/OpenShift ecosystems).
- **Nunjucks (JavaScript)**: Supports [tag-level whitespace control](https://mozilla.github.io/nunjucks/templating.html#whitespace-control) via `{%-` / `-%}` and `{{-` / `-}}` natively in template syntax out-of-the-box, matching Go's decoupled model.
- **Liquid (Ruby / JavaScript)**: Supports [tag-level whitespace control](https://liquidjs.com/tutorials/whitespace-control.html) via `{%-` / `-%}` and `{{-` / `-}}` natively in template syntax out-of-the-box.
- **Jinja (Python)**: Supports [tag-level whitespace control](https://jinja.palletsprojects.com/en/stable/templates/#whitespace-control) via `{%-` / `-%}` and `{{-` / `-}}`. Jinja also provides environment-level flags (`trim_blocks`, `lstrip_blocks`, `keep_trailing_newline`) and `{%+` to disable trimming per tag. (Note: Jinja's default environment strips trailing EOF newlines, which can be problematic for generating files that require EOF newlines).
- **Ruby (ERB)**: Supports trailing newline suppression via `-%>` (documented in [Ruby ERB Documentation](https://docs.ruby-lang.org/en/master/ERB.html#class-erb-suppressing-unwanted-blank-lines)), but does not support dedicated left-trimming (unlike Go's `{{-`) and requires enabling a caller-side execution flag (`trim_mode: "-"`). Without `trim_mode` set by the caller, using `-%>` raises a syntax error.
- **Handlebars (JavaScript)**: Supports [whitespace control](https://handlebarsjs.com/guide/expressions.html#whitespace-control) via tildes (`{{~` and `~}}`). Handlebars also includes a default behavior that automatically strips linebreaks around "standalone" helpers (lines containing only a block helper, comment, or partial surrounded by whitespace).
- **EJS (JavaScript)**: Supports [whitespace control](https://ejs.co/#docs) via `-%>` (newline slurping tag) and `_%>` / `<%_` (whitespace slurping tags). (Note: in EJS, `<%-` is overloaded to mean unescaped HTML output rather than left-trimming).

Adopting hyphen-based whitespace trimming in EEx aligns Elixir with well-established patterns familiar to developers across ecosystems.

## Critical Analysis: Pitfalls & Lessons Learned from Go's Implementation

While Go 1.6's `{{-` and `-}}` delimiters solved an urgent blank-line bloat problem, real-world usage in ecosystems like **Helm** and **Kubernetes** revealed several ergonomic and maintenance pain points. Examining these pitfalls allows us to design safer, cleaner rules for Elixir's EEx:

### 1. "Hyphen Soup" (Visual Clutter & Unreadable Code)
In Go templates, developers frequently over-apply hyphens to every tag (`{{- if .Enabled -}}{{- range .Items -}}...`), turning readable templates into unreadable "hyphen soup".
- *Elixir Lesson*: Whitespace controls should be used judiciously. In EEx, trimming is primarily designed for block-level control flow tags (`<%- if ... -%>` and `<%- end -%>`) placed on dedicated lines, rather than being sprinkled across every inline expression.

### 2. Over-Trimming & Accidental Word Concatenation
In Go, `{{-` strips *all* preceding whitespace (spaces, tabs, and newlines) up to the nearest non-whitespace character. As a result, writing `Hello {{- .Name}}` inadvertently strips the space after `"Hello"`, rendering `"HelloWorld"`.
- *Elixir Lesson*: EEx's tokenizer and compiler specification should prioritize stripping **line breaks (newlines) and line indentation** around dedicated block tags, ensuring inline spaces between words are not unexpectedly collapsed.

### 3. Destruction of Indentation Structure (The "YAML / Helm Trap")
In YAML generation, placing `-}}` at the end of a line strips the trailing newline character, pulling the subsequent line up into the current line and creating invalid YAML (`key: {{ .Val -}}\nnext_key: 123` -> `key: valuenext_key: 123`).
- *Elixir Lesson*: Proposal documentation and guidelines must emphasize using right-trimming `-%>` on dedicated block control lines (`<%- if ... -%>`), while avoiding right-trimming on line-end value outputs where the trailing newline is semantically required.

### 4. Syntax Ambiguity (`{{-` vs `{{ -` vs `{{-3}}`)
In Go, exact spacing around the hyphen is critical (`{{- .Name}}` is a trim tag, `{{-3}}` is a negative integer literal, and `{{ - 3 }}` is a syntax error in pipelines).
- *Elixir Lesson*: In `EEx.Tokenizer`, `<%-` must be recognized as a strict token sequence with no space between `<%` and `-`. Because Elixir code inside EEx tags begins *after* the tag delimiter (e.g., `<% -3 %>` vs `<%- 3 %>`), `EEx.Tokenizer` unambiguously distinguishes tag trimming `<%-` from negative numbers inside Elixir expressions.

### 5. Domain Separation: Text/Code Generation vs. HTML Component Trees
In Go, the shortcomings of `html/template` led modern HTML development toward compiled, type-safe component systems (like `templ`).
- *Elixir Context*: In Elixir, HTML UI rendering is already handled by **HEEx** (HTML EEx) with its own HTML-aware parser and format-preserving component engine. EEx's hyphen trimming specifically targets text, source code, and manifest generation (`mix new`, `phx.new`, YAML/JSON generation) where raw text line breaks are handled.

## Proposed Solution & Syntax Specification

Extend EEx tokenization and compilation to support hyphenated tag delimiters for explicit, fine-grained whitespace control:

- **`<%-` (Left-trim)**: Strips whitespace and line breaks to the left of the tag (up to the preceding non-whitespace character or newline).
- **`-%>` (Right-trim)**: Strips whitespace and line breaks to the right of the tag (up to the next non-whitespace character or newline).
- **`<%- ... -%>` (Bi-directional trim)**: Strips whitespace and line breaks on both left and right sides of the tag.

### Key Design Decision: Decoupled Template-Level Control (Go, Nunjucks & Liquid vs. Ruby ERB & Jinja)

A key design choice in this proposal is to follow **Go's, Nunjucks', and Liquid's model rather than Ruby ERB's or Jinja's model**:

- In **[Ruby ERB](https://docs.ruby-lang.org/en/master/ERB.html#class-erb-suppressing-unwanted-blank-lines)**, tag-level trimming is limited to right-side trailing linebreaks (`-%>`) and requires passing `trim_mode: "-"` to the ERB initializer. It lacks left-side whitespace trimming (`<%-`) and couples template syntax to evaluation flags (raising a syntax error if `trim_mode` is omitted by the caller).
- In **[Jinja](https://jinja.palletsprojects.com/en/stable/templates/#whitespace-control)**, whitespace control involves a complex interplay between environment-level flags (`trim_blocks`, `lstrip_blocks`, `keep_trailing_newline`), trimming tags (`-`), and override tags (`+`). Furthermore, Jinja's default environment strips trailing EOF newlines from whole template files, which is problematic when generating POSIX-compliant code or configuration files that require an end-of-file newline.
- In **Go's `text/template`**, **[Nunjucks](https://mozilla.github.io/nunjucks/templating.html#whitespace-control)**, and **[Liquid](https://liquidjs.com/tutorials/whitespace-control.html)**, both left-side (`{{-`) and right-side (`-}}`) trimming are natively supported by the template parser out-of-the-box, without requiring any execution flags passed at evaluation time or altering file-level EOF newlines.

In Elixir EEx, we propose that both `<%-` (left-trim) and `-%>` (right-trim) work **natively out-of-the-box** during tokenization. Template authors (whether in Mix generators, Phoenix, or third-party libraries) should have explicit, predictable control over whitespace trimming directly within their templates, without requiring callers of `EEx.eval_file/2` or `EEx.function_from_string/5` to configure complex environment flags.

### Choice of Hyphen (`-`) over Tilde (`~`)

While **[Handlebars](https://handlebarsjs.com/guide/expressions.html#whitespace-control)** uses the tilde character (`{{~` and `~}}`) and automatically strips lines containing "standalone" helpers by default, the **hyphen (`-`)** modifier (`<%-` and `-%>`) is proposed for EEx for two reasons:
1. **Ecosystem Standardization**: The hyphen (`-`) modifier is the dominant standard across ERB, Go, Jinja, Nunjucks, Liquid, and EJS, making `<%-` and `-%>` immediately familiar to developers coming from almost any language.
2. **Explicit vs. Implicit Behavior**: Unlike Handlebars' implicit stripping of standalone lines, hyphen modifiers in EEx offer explicit, opt-in whitespace trimming without introducing implicit line-stripping rules that could produce unexpected formatting side-effects in general-purpose text/code generation.

### Tag Delimiter Scope & Design Trade-offs

Unlike Go's `text/template` where all actions share a single `{{` / `}}` delimiter pair (making `{{-` and `-}}` trivial to define), EEx features distinct opening tag markers (`<%`, `<%=`, `<%!--`). Evaluating real-world template usage helps determine where whitespace trimming adds high value versus where it introduces visual clutter or ambiguity:

#### 1. Primary Target: Control Flow & Evaluation Tags (`<% ... %>`)

Control flow expressions (`<% if ... do %>`, `<% for ... do %>`, `<% case ... do %>`, `<%- end %>`) are the primary source of whitespace defects in EEx. Because authors place these tags on dedicated lines for readability, each tag leaves behind an unintended newline or leading indent in rendered files.

- **Proposed Syntax**: `<%-` (left-trim), `-%>` (right-trim), `<%- ... -%>` (bi-directional trim).
- **Example**:
  ```eex
  <%- if @ecto do -%>
  defp deps do
    [{:ecto, "~> 3.10"}]
  end
  <%- end -%>
  ```
- **Value**: High. Directly solves the core problem across Mix generators, Phoenix installers, and YAML manifests.

#### 2. Expression Output Tags (`<%= ... %>`)

Expression tags evaluate and output values inline (e.g. `<%= @user.name %>`).

- **Right-Trim (`<%= value -%>`)**: Replaces `%>` with `-%>` to suppress a following newline. This is visually clean and occasionally useful when an output value is immediately followed by a line break that should be collapsed.
- **Left-Trim (`<%-=` vs `<%=-`)**: Adding left-trimming to output tags creates 4-symbol sequences (`<%-=` or `<%=-`), which look visually clunky and raise questions about symbol ordering. Because leading whitespace around output expressions is almost always intentional surrounding text/formatting, left-trimming output tags is rarely needed.
- **Proposal Recommendation**: Support right-trimming (`<%= value -%>`) as a natural extension of `-%>`, but leave left-trimming focused on control flow tags (`<%-`).

#### 3. Comment Tags (`<%!-- ... --%>`)

Comments (`<%!-- comment --%>`) produce zero output text and are used purely for template documentation.

- **Trade-off Analysis**: Attempting to add trimming hyphens to HTML-style comment tags (`<%!-- ... -%>` or `---%>`) looks visually awkward and resembles a typo or eyesore.
- **Proposal Recommendation**: Keep comment tags (`<%!-- ... --%>`) simple and exclude them from trimming syntax. If a comment appears on its own line and needs newline suppression, template authors can adjust adjacent control flow tags.

#### 4. Exclusion of Deprecated Constructs

- **`<%#` is excluded**: Legacy comment tags using `<%#` are deprecated in Elixir (in favor of `<%!-- --%>`) and will be removed in Elixir 2.0. Trimming syntax will not be added to deprecated constructs.

### Examples

#### 1. Conditional Template Blocks (e.g. `mix new` / `phx.new`)

**Before (Current EEx without `trim: true`):**
```eex
# <%= @app_name %>

<%- if @ecto do %>
defp deps do
  [{:ecto, "~> 3.10"}]
end
<%- end %>
```
*Output currently contains unwanted empty lines above and below `defp deps` when `@ecto` is true, or double blank lines when `@ecto` is false.*

**After (With Proposed Hyphen Trimming):**
```eex
# <%= @app_name %>

<%- if @ecto do -%>
defp deps do
  [{:ecto, "~> 3.10"}]
end
<%- end -%>
```
*Output cleanly includes `defp deps` block without spurious leading or trailing blank lines.*

#### 2. Clean List Iteration

```eex
Dependencies:
<%- for dep <- @deps do -%>
  - <%= dep %>
<%- end -%>
```

#### 3. Indentation-Sensitive Formats (YAML / Kubernetes / OpenShift)

**Before (Unintended blank lines inside YAML block):**
```eex
env:
<%- if @port do %>
  - name: PORT
    value: "<%= @port %>"
<%- end %>
```

**After (Clean, Valid YAML Output):**
```eex
env:
<%- if @port do -%>
  - name: PORT
    value: "<%= @port %>"
<%- end -%>
```

## Potential Impact on Codebase & Community

### Impact on Elixir Core Codebase
- **Tokenizer (`EEx.Tokenizer`)**:
  - Update the state machine to recognize `-` immediately after `<%` or before `%>`.
  - Emits modified tokens (e.g., `{:start_trim_expr, ...}` or metadata flag `trim_left: true`, `trim_right: true`).
- **Compiler (`EEx.Compiler`)**:
  - When assembling AST from tokens, strip trailing whitespace/newlines from the preceding literal text token if `trim_left` is set, and strip leading whitespace/newlines from the following literal text token if `trim_right` is set.
- **Backward Compatibility**:
  - 100% backward compatible. Standard tags (`<%`, `<%=`, `<%#`) preserve their existing exact behavior.

### Performance Impact
- **Zero runtime overhead**: Whitespace trimming occurs entirely during EEx template compilation. Compiled functions output pre-trimmed binary literals.

### Community & Ecosystem Impact
- Significantly reduces template whitespace bugs in Mix generators, Phoenix installer (`phx.new`), LiveView generators (`phx.gen.html`, `phx.gen.live`), Igniter, and third-party code generator libraries.
- Improves reliability when using EEx to generate whitespace-sensitive formats like YAML/JSON (such as in Kubernetes/OpenShift tooling or deployment scripts).
- Simplifies template authoring and maintenance by removing the need for awkward single-line tag tricks or post-processing scripts.
